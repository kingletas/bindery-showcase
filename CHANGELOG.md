# Changelog

## Unreleased

- The repository exists: a Go module, a `make check` that fails on any gofmt difference and runs `go vet ./...` and `go test -race ./...`, and a CI workflow that runs that same target.
- `bindery-guard` reads one tool call as JSON on standard input and runs four guards against it. It exits 0 and prints nothing when every guard is silent, and exits 2 with the guard's name and one sentence of reason on standard error when one refuses. A call that is not valid JSON of the expected shape is refused too.
- Shell is read with `mvdan.cc/sh/v3/syntax`, the module's one dependency, and walked as a tree. A destructive command is found after `&&`, inside `$(...)`, in a pipeline, inside `bash -c`, and behind wrappers such as `timeout`, `nice`, `env`, `sudo` and `xargs`, including when the command name is written `$'rm'`. A line the parser rejects, which includes syntax only zsh accepts, is refused with a reason that says the command could not be read, and so is a part of the line that is only known at run time.
- The `recursive-delete` guard refuses `rm -r` and `find -delete` on `/`, the home directory, a workspace root itself or anything outside the workspace roots. The `force-push` guard refuses a forced push or a delete on a protected branch. The `pipe-to-shell` guard refuses a download that is run as it arrives. The `secrets-read` guard refuses a read of a file that matches a secrets pattern. Roots, branches and patterns come from `BINDERY_WORKSPACE_ROOTS`, `BINDERY_PROTECTED_BRANCHES` and `BINDERY_SECRET_PATTERNS`, with defaults that name no real path.
- An unknown word where an option could stand is not skipped. `rm $OPTS /srv/x` is read as a possible recursive delete and `git push $F origin main` as a possible force-push, and both are refused when the target is protected, outside the workspace or unknown. `rm "$file"` alone stays silent. An unquoted unknown word may split into a flag and a target, so `rm $X`, `rm $(cat list)`, `"$@"` and the input of `xargs rm` are read as possible recursive deletes, `find` with an unknown word is read as a possible `-delete`, and `bash $X` is unreadable.
- `pipe-to-shell` also refuses a download piped into a shell or interpreter that is told to read its script from stdin by name (`bash /dev/stdin`, `sh /dev/fd/0`, `bash -`, `python3 /dev/stdin`), and one given an operand that is only known at run time.
- `bindery-guard` exits 2 when it is started with an argument it does not take, with the usage on standard error. It has no other non-zero exit code, so a hook that blocks only on 2 does not let calls through when the runner is misused.
- A command the scanner does not know is read as a possible runner: its words are searched for the first one that names a tool the guards read, and the rest is read from there as the command it runs, so `flock`, `watch`, `parallel`, `systemd-run`, `script -c`, `su -c`, `runuser`, `chroot`, `busybox` and `toybox` are looked through without being listed. Words holding spaces or operators are read as command strings. Words-only commands such as `echo` and `printf` are exempt. The text of an `alias` and the action of a `trap` are read as command strings.
- `make demo` builds the runner and pipes two invented calls through it, one refused and one silent, and fails if either exit code is wrong.
- The README table points the first three claims at their files and tests, and documents the call's JSON shape, the exit codes and the configuration. The message bus is still marked "not built yet".
- `bindery-gate` is the commit gate, a small one. It reads the staged change with `git diff --cached`, sends each changed path to the lanes of a table, runs each matched lane's check once, and refuses the commit if any check fails. It runs as a git `commit-msg` hook, which is handed the message file, or by hand against the staged change. It exits 0 and prints nothing when the commit may go ahead, 1 with one line per failing lane or rule on standard error when it refuses, and 2 when it could not do its job, so a hook never lets a commit through because the gate failed to run.
- The lanes table is a tab-separated file, `lanes.tsv` at the repository root unless `BINDERY_GATE_TABLE` names another. Each row is a lane name, a path pattern and a check command. A check is split on whitespace and run without a shell, and a row that holds shell syntax or starts with an assignment is refused. A table that cannot be read is refused whole. A path that no lane claims refuses the commit and is named. The table shipped for this repository has four lanes: go, docs, workflows and examples.
- A commit that modifies, deletes or renames away an existing test file must carry a `Test changed: <why>` line in its message, or the gate refuses it. A new test file needs no line. Under a commit with a pathspec, the gate judges what that commit commits and not everything staged.
- `examples/commit-msg` is the two-line hook that runs the gate.
- `make demo` also runs the gate in a throwaway repository under a temporary directory that it removes: a commit that breaks a lane is blocked, an edited test with no reason line is refused, and the same edit with the line goes through. Nothing in it needs the network.
- The README table points the gate's two claims at their files and tests, and a new section documents the table format, the test rule, both ways to run the gate, its exit codes and its limits.
